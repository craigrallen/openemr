# Transactions dashboard help in the workbench

OPEMR-90 phase two adds a screen palette to the existing Transactions dashboard help document. It is a presentation slice, not clinical or popup acceptance. The original 6,815 route bytes are recoverable by removing exactly the new `<style>` block and replacing the body class marker with `<body>`. The four sections, translated instructions, sample buttons, warnings, links, PHP setup, and their historical wording remain unchanged. Historical instructions are preserved as source content, not endorsed as current workflow or privilege policy.

## Source path and scope

`interface/patient_file/transaction/transactions.php` takes `pid` from the active patient session (`get('pid', 0)`), sets `show_help_icon => true` and `help_file_name => "transactions_dashboard_help.php"`, constructs `OemrUI`, includes `interface/patient_file/summary/dashboard_header.php`, and later calls `oeBelowContainerDiv()`. The included header passes `OemrUI::pageHeading()` to `templates/patient/dashboard_header.html.twig`, which renders `{{ pageHeading }}`. `OemrUI` uses `enable_help` and `show_help_icon` to determine help-icon eligibility. These settings explain this caller's help path; they do not prove that every authenticated role can open it.

The generated help action targets `#myModal` with Bootstrap's `data-toggle='modal'`. That ordinary `.modal` contains `targetiframe`, whose `src` is filled from `data-src` on the first help click. The help document calls `Header::setupHeader()`, through which the existing popup assets autoload. The source-derived frame path is `targetiframe` → `contentframe` → workbench shell. `popup.js` follows that same-origin ancestry and adds `oe-workbench-context` to the help document's `<html>` while the shell is active. This path supplies **CONTEXT** only: the modal does not have `dialogModal`, and the help document is not a workbench popup class case. The scoped selector therefore requires both `html.oe-workbench-context` and `body.oe-transactions-dashboard-help-popup`.

The caller's Delete link is individually guarded by `AclMain::aclCheckCore('admin', 'super')` inside each transaction row. There is no equivalent new authorization rule in this help change, and the pre-body caller source does not establish a page-wide ACL check. The preserved help prose about “adequate privilege” and Administrator privileges cannot substitute for actual access checks. Role, patient-session, and transaction-action behavior need live verification before any broader claim.

## Presentation change

The body marker is present in the DOM in every medium. The style itself is inside `@media screen`, so it supplies no print rule. Five selectors pair the workbench palette with its fallback: canvas `#f3f7f5` and ink `#17343b` on the body; paper `#fff` and ink on the direct help container; paper and ink on help headings; transparent background and petrol `#086878` on non-button links and redirect icons. The two `!important` declarations are limited to the heading background and redirect color because the existing shared help theme declares important values for those exact properties. No selector changes geometry, typography, behavior, controls, or semantic warning colors. The non-button link selector leaves `.btn` controls alone, and existing `text-primary` descendants of external-link icons remain explicitly styled by their theme.

The new paper backdrop may still change effective contrast for semantic icons, sample buttons, focus indicators, and external-link icons. CSS source inspection alone cannot establish their native computed colors across themes. These combinations remain an explicit visual review gate.
