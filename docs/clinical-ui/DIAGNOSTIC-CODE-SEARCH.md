# OPEMR-223 DiagnosticReport code search

## Change and acceptance boundary

The original DiagnosticReport aggregator selected the first child service supporting the first code token. A code supported by both clinical notes and laboratory reports could therefore omit a result. For code queries without explicit `_count`, `_offset`, or `_sort`, the code branch now splits a comma-separated string for service selection and selects every child supporting any token. It passes the original search parameters and patient bind unchanged to each selected child. One selected child returns its ProcessingResult directly, preserving result identity, pagination, and its own data and error state. Multiple selected children use the existing `searchServices` aggregation. If none supports a code, the existing `getServiceForCode` exception supplies the validation error. The native laboratory service reports support for every code; the unsupported-code fixture check uses a synthetic compatibility seam.

When `_count`, `_offset`, or `_sort` is present, including `_count=0`, routing retains the original `getServiceForCode` call on the raw code value and returns that first child's ProcessingResult directly. A comma-separated value remains unsplit for this selection, as in the original branch. Code union with explicit pagination or sorting remains open. QueryPagination has a source-backed default limit of 0, so the new union path is limited to queries without explicit paging or sorting controls; it is not a unified global paging implementation.

Category continues to take precedence over code, and searches without code continue to use `searchAllServices`. For a multi-service code search, `searchServices` combines child data and errors, clears accumulated data when a child reports an error, and stops before later services. Its ProcessingResult merge does not preserve child pagination or continuation metadata. A single selected service instead returns its child result directly. The static REST controller constructs a bundle from result data with `createBundle(..., false)` and does not forward result pagination; that source observation is not runtime proof of REST behavior. Complete DiagnosticReport query fidelity is not established.

The change is confined to the approved DiagnosticReport code branch. The fixture's whole-source inverse checks preservation of the original source outside that block against SHA-256 `d1f7069a77b8a438b8ecd0737762c13f6eacdb3df29e8fbd557a2ff7b6faca38`. There is no shared-helper, query-model, SQL, configuration, dependency, or cron change.

These are controller-executed results, not independent runtime attestation.

The fixture loads the native DiagnosticReport aggregator, mapped-service and patient traits, token search classes, FHIR search-field factory, ProcessingResult, and QueryPagination. It uses declaration-only framework seams, a fixed logger seam, constructor bypass, and a recording projected-row child backend. Its checks cover shared and single-service routing, comma-separated tokens, prefixed tokens, forwarded parameters and patient bind, category precedence, no-code aggregation, child errors, unsupported-code compatibility, child result identity and pagination, and legacy routing with explicit `_count`, `_offset`, and `_sort`, including zero count and an unsplit comma-separated code value.

The fixture's flat-array token checks call the native field factory directly from the synthetic child backend. They demonstrate that seam's OR matching; they do not establish native public-query OR semantics for repeated parameters. `ResourceServiceSearchTrait` groups raw array values as repeated-parameter AND before the native field factory. This code branch passes those arrays unchanged to real children. Repeated-array AND behavior, system-aware SQL matching, and the complete search pipeline are not runtime accepted by this fixture.

This is bounded source and fixture evidence. It does not exercise the full native child services, ListService, SQL, an authenticated FHIR request, or a runtime REST request. Authenticated FHIR behavior, roles and security, persistence, clinical QA, hosted coverage, independent review, and ordinary approval remain open. The change is unmerged and undeployed. It does not establish UI coverage, all 22 paths, Swedish completeness, or whole-FHIR conformance.
