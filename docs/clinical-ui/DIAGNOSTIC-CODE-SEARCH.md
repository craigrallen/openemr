# OPEMR-223 DiagnosticReport code search

## Change

The original aggregator routed a code search to the first child service supporting the first token. A code present in both clinical notes and laboratory reports could therefore lose the laboratory result. Comma-separated OR values could also lose results when their codes belonged to different services.

The code branch parses comma-separated values for service selection and asks the existing mapped-service trait for every supporting service. When exactly one service matches, it returns that child's ProcessingResult directly, preserving its identity and pagination, including the continuation metadata. When multiple services match, it uses the existing searchServices aggregation to combine their data. The original search parameters and patient bind pass to each selected child; the native child search-field factory parses raw token and comma-separated input. If no service supports a code, the existing getServiceForCode exception supplies the validation error. The native laboratory service reports support for every code, so the unsupported-code check uses a synthetic compatibility seam.

Category takes precedence over code and continues to use its existing child selection. Searches without code continue to use searchAllServices. In the multi-service path, the existing aggregator combines validation and internal errors, clears accumulated data on an error, and stops before later services. A single selected service instead returns its own ProcessingResult directly, including its own error and data state. No global merge or pagination policy is added.

The multi-service aggregation does not preserve child pagination or continuation metadata. This is an inherited limitation now exposed for cross-service code unions; cross-service pagination is not accepted as complete. The static native REST controller constructs its bundle from result data with createBundle(...false) and does not forward result pagination. That source observation is not runtime proof and does not remove the service-level metadata limitation. The single-service route does not silently lose its child's continuation metadata.

Only the approved DiagnosticReport code branch changes. The legacy import and other source bytes remain as supplied. There is no SQL, filter, shared-helper, baseline, dependency, configuration, merge, deployment, or cron change.
