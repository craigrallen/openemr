# OPEMR-227 Questionnaire list errors

The public `list()` route returns the response produced by `getAll()` directly. On an error, `getAll()` passes the native `ProcessingResult` and success-code argument `200` to `RestControllerHelper::handleFhirProcessingResult()` before reading data or building entries. That helper returns a Symfony HttpFoundation `Response`, while the controller requires a PSR `ResponseInterface`. The error branch now converts the helper response with `PsrHttpFactory` and one `Psr17Factory` supplied to all four constructor positions. Healthy searches still build a Questionnaire Bundle and serialize it once, including an empty Bundle when the service has no errors and no data.

An independent review identified this P1 type mismatch. The earlier provisional GREEN from the 19-case controller fixture reflected its synthetic helper returning a PSR response; it did not establish native return-type acceptance. The corrected CLI fixture keeps the repository controller, `ProcessingResult`, and `QueryPagination`, and models the helper error as a synthetic Symfony Response. Its synthetic bridge checks the four factory identities and converts that exact response to a PSR sentinel. The 19 cases cover a pinned whole-source inverse, 12 error paths across staff and patient requests, and six healthy paths. The inverse requires exactly one complete bridged error fragment and restores it, together with the other approved changes, to the pinned original. Against the supplied current source, the 12 error paths are designed to fail with a PHP return `TypeError`; after the bridge change, they are designed to pass. The Jest adapter requires one LF-terminated JSON report with 19 passing cases and empty stderr. These are test expectations, not execution claims.

The fixture uses synthetic request, service, Bundle, helper, and bridge boundaries. It does not verify real Symfony-to-PSR conversion, actual HTTP status or body serialization, SQL behavior, security, persistence, clinical acceptance, UI behavior, Swedish readiness, or acceptance of the original 22 features. The helper's `200` argument is its success-code parameter and does not assert an error HTTP status. Ordinary approval, hosted exact-head complete gates, and authenticated native security, persistence, and clinical QA remain open.
