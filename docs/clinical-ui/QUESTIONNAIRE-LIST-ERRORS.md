# OPEMR-227 Questionnaire list errors

The public `list()` route now returns the response produced by `getAll()` directly. After the Questionnaire service call, `getAll()` sends any native `ProcessingResult` error to `RestControllerHelper::handleFhirProcessingResult($processingResult, 200)` before reading data or building entries. Healthy searches still build a Questionnaire Bundle and serialize it once, including an empty Bundle when the service has no errors and no data.

The CLI fixture loads the repository controller, `ProcessingResult`, and `QueryPagination`. It uses synthetic request, service, Bundle, and response boundaries. Its 19 cases include a pinned whole-source inverse check, validation, internal, and combined errors with empty or poison data through both staff and patient public list paths, plus healthy empty, multiple-resource, and missing-`REDIRECT_URL` searches in both paths. The Jest adapter runs the fixture and requires one LF-terminated JSON report with 19 passing cases and empty stderr.

This supports Questionnaire interoperability only. It does not establish acceptance of the original 22 features, UI behavior, Swedish readiness, real HTTP status or helper serialization, SQL behavior, security, persistence, or clinical acceptance. The helper's `200` argument is its success-code parameter, not a claim that errors receive HTTP 200. Ordinary approval, hosted exact-head complete gates, and authenticated native security, persistence, and clinical QA remain open. This is scheduled allocation 1/max2, counting implementation AND QA; a second run is not mandatory, and unchanged polling is not delivery. No merge, deployment, master, database, patient, national, vendor, Swedish publication, audit restart, or cron change is included.
