# OPEMR-203: CarePlan activity end dates

The native `CarePlanService::search()` query already selects `fcp.date_end`. Before this change, `createResultRecordFromDatabaseResult()` moved each row's `date` into its activity detail but left `date_end` on the record. Search aggregates later rows by appending only their details, so their end dates were lost and the first row's end remained at plan level.

The mapper now copies each non-null `date_end` into that row's detail and retains the original top-level value. The existing `FhirCarePlanService::parseOpenEMRRecord()` uses each detail's end for `activity.detail.scheduledPeriod.end` and the latest detail end for the CarePlan period. Retaining the top-level end also preserves `FhirGoalService` target `dueDate`, which reads it from the same mapper's output. This change does not alter FHIR parsing, date conversion or choice, third-party metadata, status, proposed-date behavior, or the existing independent `scheduledPeriod` plus `scheduledString` issue.

## Verification and boundaries

The committed, read-only fixture `tests/clinical-ui/fixtures/careplan-activity-end.php.fixture` invokes the actual native CarePlan mapper, complete native `FhirCarePlanService` and `FhirGoalService` parsers, FHIR models and helpers, and `CodeTypesService` with an explicit synthetic global `code_types=[]` and no-code Goal inputs. It uses reflection and constructor bypass. Its `mapRows()` function composes native mapped rows to match the search loop's detail append; it does not execute SQL or the native search loop. The fixture uses an explicitly synthetic identity `BaseService` because the real parent loads `code_types.inc.php` and site SQL configuration, a declaration-only `FhirServiceBase`, and a synthetic global `text()` helper. Native parent UUID conversion and narrative escaping are therefore outside its coverage.

The initial 20/20 pass was incomplete: independent P2 review found that moving `date_end` removed the top-level value used by the shared Goal parser. A subsequent tests-only commit (`055f2a25`) preceded this correction. Its actual controller RED run had 32 cases, 21 passes, and 11 failures, including a distinct datetime Goal end mapped to the wrong `dueDate` and an end-only Goal missing `dueDate`. The corrected fixture passes 32/32. Cases cover single and multiple activities, distinct and reversed end dates, end-only, start-only, and null-end inputs, plus native Goal target due dates and direct FHIR object and encoded output. UTC fixtures give fixed expectations, not a daylight-saving or timezone policy. Passing these cases supports the mapped end-date interoperability path; it does not establish completion of the original 22 features, UI, Swedish, or full FHIR readiness. SQL/search execution, real aggregation, authentication, roles, security, persistence, and clinical QA remain open. Ordinary approval and hosted gates are separate; this work does not authorize merge or deployment.
