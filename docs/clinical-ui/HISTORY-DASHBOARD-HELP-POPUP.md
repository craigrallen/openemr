## Caller and activation

`interface/patient_file/history/history.php` takes the patient ID from the active session (`pid`, default `0`). It requires `patients/med`; if the patient has a `squad`, it also requires that squad's ACL. Denied viewers receive the existing “History not authorized” response. After eligibility, the route reads history data; when `getHistoryData($pid)` is not an array, it calls `newHistoryData($pid)` and reads again. A plain GET can therefore create a history row. Do not execute the route as a read-only verification or perform a browser/prefetch probe against patient data.

The route configures OemrUI with `show_help_icon` and `history_dashboard_help.php`. Its dashboard header inclusion and page heading are inside the separate `patients/med` `write` or `addonly` gate. Thus the help entry point is not promised to every otherwise eligible viewer. OemrUI also checks its `enable_help` setting when offering help. The ordinary `#myModal` modal contains `#targetiframe`; its delegated first click copies `data-src` to `src` once, so the help file loads lazily.

The help iframe can sit under a `contentframe` beneath the active same-origin workbench shell. The existing `popup.js` walks that ancestor chain and applies `oe-workbench-context` to the iframe document's `<html>` while the shell is active. It removes the class on deactivation or page hide. This ordinary modal iframe does not gain `oe-workbench-popup`, which is reserved for actual popup context. The new CSS keys off the context class only. No caller, OemrUI, popup controller, theme asset, or eligibility code is changed here.
