# OPEMR-199: FHIR AllergyIntolerance criticality

The native `AllergyIntoleranceService::search()` reads allergy rows from `lists` (`src/Services/AllergyIntoleranceService.php:46-115`); its `insert()` and `update()` write allergy records (`:256-285`, `:302-362`). The FHIR service delegates search to that service (`src/Services/FHIR/FhirAllergyIntoleranceService.php:506-508`) and maps each returned record in `parseOpenEMRRecord()` (`:109`, `:146-163`). `FhirServiceBase::getAll()` calls the search and parser (`src/Services/FHIR/FhirServiceBase.php:328-338`); the AllergyIntolerance REST controller calls `getOne()` and `getAll()` (`src/RestControllers/FHIR/FhirAllergyIntoleranceRestController.php:140`, `:216`). The FHIR service also delegates inserts and updates to the native writer (`src/Services/FHIR/FhirAllergyIntoleranceService.php:456-462`, `:472-497`).

Only a recognized string `severity_al` key sets FHIR `criticality`. The eight existing mappings remain unchanged: `mild`, `mild_to_moderate`, `moderate` → `low`; `moderate_to_severe`, `severe`, `life_threatening_severity`, `fatal` → `high`; `unassigned` → `unable-to-assess`. Omitted, null, empty, and unrecognized values omit the optional field; keys are not trimmed or case-normalized. This preserves the inherited severity-to-criticality mapping and introduces no clinical risk policy. The [FHIR R4 AllergyIntolerance definition](https://hl7.org/fhir/R4/allergyintolerance.profile.json) gives `criticality` cardinality 0..1 and says a missing value means unknown, though it may be known elsewhere.
