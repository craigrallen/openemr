# OPEMR-122: observation end-date validation

## Change and rationale

`ObservationService::validateObservationData()` checks a nonempty `date_end`, but previously passed `date` to `DateFormatterUtils::dateStringToDateTime()` in that block. A malformed end date could therefore pass validation, an end date before the start could not be detected, and a supplied end date with a missing start could read an undefined `date` key and raise a `TypeError`. The end-date parse now reads `date_end`. Its bounded parse block first uses the configured display formatter. Only when that returns `false`, it tries the canonical stored `Y-m-d H:i:s` representation. The existing start-date parse, error messages, optional-end check, and date comparison remain as they were.

The initial review found a P2 edit regression: `processEnhancedFormSave()` retains an existing record's database `date_end` when the post omits it, then validates that canonical `Y-m-d H:i:s` value with the configured display parser, which normally expects no seconds and may expect US or international date order. Such records can fail validation during an otherwise ordinary edit. The P2 is resolved by the bounded fallback: only after the display parse returns `false`, it parses with `!Y-m-d H:i:s` and accepts the result only if formatting it back as `Y-m-d H:i:s` exactly matches the original string. Failed or mismatched candidates retain the existing `Invalid end date format` result. Valid localized display values retain the display parser's permissive rollover behavior. An accepted end is compared as a `DateTime` against the parsed start; an earlier end retains `End date cannot be before start date`. This service contract follows the actual caller; an observation ID does not establish the value's provenance or authorize it. This validation boundary changes neither input normalization nor the write path, and does not establish save atomicity, authenticated persistence, or clinical acceptance.

## Consumer and limits

The enhanced observation template, `interface/forms/observation/templates/observation_edit.html.twig`, posts to `interface/forms/observation/save.php`. That entry point calls `ObservationController::saveAction()`, then `processEnhancedFormSave()`. The controller permits `date_end` among submitted clinical fields and calls `ObservationService::validateObservationData()` before calling `saveObservation()`. The service's write path also has a `date_end` value, but this isolated test does not exercise a write.

The final Astra review reported no P1 or P2 findings. Its sole P3 was the test comment's incorrect claim that parsing an explicit minute inherits current seconds; that comment is corrected, and the four new cases assert exact equality between displayed `:30` and stored `:30:00`. Existing `:30:59` cases still cover a later value in the same minute.

The current edit template renders a `date` input but no `date_end` input, and `interface/forms/observation/observation.js` checks the required start date without end-date validation. This regression covers the service boundary for callers that supply or retain `date_end`; acceptance of the original feature4 side-by-side-records workflow remains unverified, as do an end-date UI flow and a user-visible clinical result. The canonical round-trip check enforces the stored string shape and calendar value, but it does not settle ambiguous local wall times at daylight saving transitions. The legacy display parser still allows calendar rollover and uses the configured local timezone. The controller's authenticated endpoint, roles, persistence behavior, and clinical QA remain to be checked. Ordinary approval and hosted CI/codecov gates are pending; no hosted gate result is claimed here.
