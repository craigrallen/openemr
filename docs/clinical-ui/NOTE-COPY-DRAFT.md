# Note copy draft foundation (OPEMR-184)

Original clinical UI requirement 5 is to copy text from an existing record or note into a new note while leaving the source unchanged. This is a bounded, in-memory foundation for that requirement. The existing SOAP reference module already copies eligible, unlocked previous SOAP sections; this helper does not replace that behavior or imply that the Copy UI is absent elsewhere.

`appendNoteCopy(request)` is exported from `interface/clinical-workspace/note-copy-draft.js` as CommonJS. It is not loaded into the browser or attached to a global. The caller supplies `{ source: { patientId, noteId, text }, draft: { patientId, text } }`; required fields must be own data properties. The helper reads no unrelated properties, does not mutate either input, and returns a fresh `{ text, provenance }` value. `provenance` contains the supplied patient ID and source note ID plus the copied text's `start` and exclusive `end` offsets in UTF-16 code units. It is caller-supplied attribution, not authorization or audit truth.

Patient and note IDs must be canonical positive ASCII decimal **strings** of 1 to 20 characters. They are neither UUIDs nor coerced numbers. Source and draft patient IDs must match exactly. Copied source text must be nonempty, at most 65,536 UTF-16 code units, and contain no NUL or lone surrogate. Existing draft text may be any string, including preexisting NUL or lone surrogates, and is preserved verbatim. A nonempty draft gets exactly `\n\n` before the copied source. The complete result, including that separator, may contain at most 262,144 UTF-16 code units. Failures use constant generic TypeError or RangeError messages. Required-field descriptor failures are normalized; this contract makes no plain-object or general proxy guarantee.

The tests in `tests/js/note-copy-draft.test.js` were committed before this production implementation, and the controller and wrapped tests agent observed the missing-module RED. The direct test run is the implementation GREEN check. The helper performs no source retrieval, authorization, patient-switch or encounter checks, dirty tracking, locked/e-sign checks, CSRF or save handling, audit write, browser integration, or accessibility behavior. An integration must revalidate source eligibility, patient and encounter context, lock state, and permissions at the time of copy and save. The source is unchanged in memory by this helper; no database or audit invariance is established here. Native clinical and UI gates remain open.
